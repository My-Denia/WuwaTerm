# ADR 0018: Semantic review keeps model findings and dictionary constraints apart

- Status: Accepted (contract and engine)
- Date: 2026-11-10
- Related: [ADR 0006](0006-dictionary-first-before-llm.md),
  [ADR 0017](0017-contextual-term-references.md),
  [ADR 0019](0019-document-context-and-human-precedents.md)

## Problem

`POST /v1/reviews` (`review-v1`, `review-v2`) checks a submitted translation
against the official dictionary. It catches a wrong or missing official name,
and nothing else: a dropped clause, a flipped negation, a changed number or a
pronoun pointing at the wrong person passes untouched. Clients want those
findings too, and only a model can produce them.

A model finding is a different kind of evidence from a dictionary finding. It
can be wrong, it is not reproducible, and it costs a model call. Mixing the two
would weaken the property clients rely on most: that `/v1/reviews` is
deterministic, free and auditable.

## Decision

Semantic review is a separate, opt-in, model-backed path:
`POST /v1/semantic-reviews` with `review_version: "semantic-review-v1"`.

1. **Separate tracks.** `/v1/reviews` keeps calling no model, costing nothing
   per request and returning the same report for the same input and
   dictionary. Its request, response, verdicts and coverage do not change. A
   client that wants both kinds of finding calls both endpoints.
2. **A model finding never becomes a `verified_constraint`.** The semantic
   response has no `verdict` field at all; every issue has
   `origin: "model"`.
3. **`verified_constraint` means a surface match.** It says that an official
   form appears in the corresponding region (`review.py`), not that the word
   carries the official sense there. Prompts and documentation say "surface
   match", never "confirmed".
4. **No document-wide sense lock and no document-wide certification.** Core
   does not derive a cross-segment "this word means X everywhere" memory from
   review results, and a review never certifies a whole document (MY-16).
   Human choices travel only as occurrence-scoped precedents (ADR 0019).
5. **Capability gate.** `GET /v1/capabilities` (meta scope, its own probe
   limit, no business allowance) lists `semantic-review-v1` and
   `translation-context-v1` only when this process can actually serve them.
   A server without the path answers 404, which a client reads as "no optional
   capabilities". `/v1/meta` is unchanged.

The contract shipped first; the engine (`wuwaterm.semantic_review`) is wired
in behind it. With no model configured, `GET /v1/capabilities` lists nothing
and `POST /v1/semantic-reviews` validates the request and answers
`llm_unavailable` (503) without calling a model.

## Contract

The request and response shapes are published in `docs/api/openapi.json`.
Fixtures generated by the real serializer are in
[`contracts/semantic-review-v1/`](../../contracts/semantic-review-v1/). This
section records the rules a schema cannot express.

### Request

- One already-paired segment: `source` and `target`, each at most 2,000
  Unicode scalars. A longer side is `input_too_long` (422), the same answer
  `/v1/reviews` gives, so clients keep one branch. Any other malformed body is
  `invalid_request` (400): unknown keys at any level, a wrong enum, a field
  over its limit, an isolated surrogate. Empty sides are accepted; the engine
  makes no model call for them.
- `context.before` (optional, read-only, never reviewed): the previous
  segment's source and target, each at most 400 scalars.
- `precedents` (at most 12): human choices from the same manuscript, shaped as
  in ADR 0019. `rendering` is null exactly when `choice` is `not_a_term`.
  `scope` has one value, `occurrence`.
- The API and the Web proxy both cap the request body at 32 KiB. Every field
  at its scalar limit in CJK is about 23 KB; escapes can push past that, so a
  client measures its serialized request and drops the farthest precedent
  first, then shortens context. `near-limit-request.json` is a valid request
  just under the cap.
- Segmentation and pairing for longer texts follow
  [segmentation-v1](../segmentation-v1.md); only `ready` pairs are sent.

### Response

- `status` is `complete` or `not_reviewed`. Model output that fails validation
  is not retried: the answer is HTTP 200 with `status: "not_reviewed"`,
  `status_reason: "invalid_model_output"`, `checked: []` and no issues. An
  empty `checked` list says nothing was checked; it is not an all-clear.
  Budget and upstream failures keep their existing HTTP error codes.
- `checked` on a `complete` response lists the seven categories:
  `omission`, `unsupported_addition`, `meaning_shift`, `negation_change`,
  `quantity_change`, `reference_inconsistency`, `term_sense`.
- **Anchoring.** The model returns quotes; the server locates them in the
  segment. A quote is placed when it occurs exactly once in its side; if it
  does not occur verbatim, a second pass ignores differences in whitespace
  runs (segmentation-v1 whitespace) and again needs exactly one match. Either
  way the span is a slice of the submitted text, never the model's text. An
  issue with a quote that cannot be placed, or with no quote at all, is
  dropped and counted in `dropped_unanchored`. A suggestion may quote its own
  replaced range (`suggestion.target_quote`, default: the issue's target
  quote); a suggestion that cannot be placed, or that replaces a range with
  the same text, is dropped and the issue kept. Span offsets are Unicode
  scalars within the segment; the client adds the segment start. At most one
  of the two spans may be null.
- **Executable text is never shortened.** `source_span.text`,
  `target_span.text` and `suggestion.target_span.text` are always the complete
  slice of the submitted side. `source_excerpt`/`target_excerpt` are display
  only: the span text when it is at most 200 scalars, otherwise the first 95
  scalars, `…`, and the last 95. Locating, highlighting, diff previews and
  replacing use the span, never the excerpt. (A Web probe showed why: applying
  a 240-scalar replacement to a 300-scalar range shortened to 200 left 100
  scalars of the old text behind, 340 scalars in all.)
- **Suggestion as a unit.** `suggestion.target_span`, its text and
  `replacement` are kept together or removed together. When the range is
  longer than 200 scalars the issue stays (spans, excerpts, rationale) but
  `suggestion` is null, `alternatives` is empty and `suggestion_withheld` is
  `span_too_long`; when the replacement is longer than 240 scalars it is
  `replacement_too_long`. A client then offers "adjust" and "ignore", not
  "accept". Before applying any replacement a client checks that
  `target_span.text` still equals the current translation at `[start, end)`.
- `alternatives` holds at most one entry; an alternative longer than 240
  scalars is skipped. `rationale` is at most 240 scalars (longer text is cut to
  239 plus `…`; it is display text, never applied).
- `term_effect` reports a fact about applying the suggestion, computed by
  running `review-v2` on a copy: `alters_official_match` (removes an official
  form that matched before), `introduces_official_form`, `none` or
  `not_checked`. Neither value means "conflict": replacing a mistranslated
  character name with an ordinary word can be the correct fix.
- `confidence` (`high`, `medium`, `low`) is self-reported by the model and not
  calibrated.

### Identity and order

- `id` = the first 32 hex digits of SHA-256 over the compact JSON array
  `[category, source_revision, target_revision, [s_start, s_end] | null,
  [t_start, t_end] | null]`. It binds a finding to one occurrence in one text
  version.
- `fingerprint` = the first 32 hex digits of SHA-256 over
  `[category, quote_s | null, quote_t | null]`, where each quote is normalized
  with NFKC, case folding and collapsing each run of
  [segmentation-v1 whitespace](../segmentation-v1.md#definitions) to one space
  (trimmed). Only the server computes it. It finds candidates across
  revisions; it never decides anything on its own (ADR 0019, re-review rule).
- JSON arrays (not `|`-joined strings) keep the inputs unambiguous.
- Order: confidence (`high`, `medium`, `low`), then source start (null last),
  then target start (null last), then category in the order above, then `id`.
  After sorting, only the first issue of each `id` is kept, so the most
  confident copy of a duplicate survives. Duplicates are not counted as
  omitted.

### Byte budget

The Web proxy refuses an upstream body over 65,536 bytes. A CJK scalar is
three bytes, a quote two, a control character six, and since spans are never
shortened one issue can be tens of kilobytes. So the server measures, not
estimates:

1. At most 16 issues are candidates, in the order above.
2. Issues are added one at a time. After each addition the whole response is
   rendered with its final counters (`omitted_issues`, `dropped_unanchored`,
   `truncated`, `truncated_reason`) and serialized exactly as Starlette's
   `JSONResponse` does (`ensure_ascii=False`, compact separators). If it
   exceeds `SEMANTIC_RESPONSE_BYTE_BUDGET = 57,344` bytes (56 KiB, leaving
   8 KiB under the proxy cap), that issue is taken back and the fit stops.
3. Everything not returned is counted in `omitted_issues`.
   `truncated_reason` is `byte_limit` when the budget removed at least one of
   the 16 candidates, otherwise `issue_limit` when there were more than 16.
4. An issue that does not fit is dropped whole. The worst single issue (both
   sides 2,000 control characters, every field at its limit) is about 33 KB,
   so the first issue always fits; a test holds that.

`max-response.json` is the serializer's own output for a synthetic worst
case: within 1 KiB below the budget, a two-digit `omitted_issues`, and one more
issue would exceed the budget. The Web contract test is to send it through the
real proxy route once Web pins this contract.

### Calls and logging

- At most one model call per request (none when both sides are blank), with
  `max_tokens` 4,096 and `response_format: json_object`
  (`WUWATERM_SEMANTIC_REVIEW_JSON_MODE=0` leaves the latter out for a gateway
  that refuses it); the engine must keep the per-segment P95 under the 45 s
  model timeout. Blank output, output that is not the agreed JSON object, an
  unknown category or confidence, or a mistyped field makes the whole answer
  `not_reviewed`; nothing is retried.
- Provider reasoning is switched off by default: the request carries
  `thinking: {"type": "disabled"}`. The production model (DeepSeek) thinks by
  default at high effort, and `max_tokens` also pays for that hidden
  reasoning: in the first smoke run every 4,096 tokens went to reasoning,
  `finish_reason` was `length` and the content was empty, about 28 s per
  call. With thinking off the same segment answered valid JSON in about 4 s;
  with `reasoning_effort: low` in about 15 s.
  `WUWATERM_SEMANTIC_REVIEW_THINKING` picks `disabled` (default), `low` or
  `high` (thinking on at that effort, `max_tokens` 16,384), or `omit` (send
  neither field, for a gateway that refuses them). Translation requests are
  unchanged.
- The prompt gives the model the dictionary facts of `review-v2` for the same
  pair, worded as surface matches ("the corresponding region contains the
  official form X; this is only a surface match"), and the human precedents
  with the fixed wording of ADR 0019. All texts go in as JSON string values,
  so a text cannot close or reopen a prompt section. Semantic review
  shares the translation path's per-process call budget, concurrency limit and
  per-device rate limit; there is no new budget mechanism.
  `WUWATERM_SEMANTIC_REVIEW_MODEL` may name a different model and defaults to
  the translation model.
- The untrusted-source instruction of the translation prompt applies; every
  text field is plain text to every client.
- Nothing is written to disk and no text is logged. The log line carries the
  redacted device, the request id, the two input lengths, the issue count, the
  unanchored-drop count and the status. Every HTTP attempt to the gateway also
  logs one line with its purpose, outcome class, status and elapsed time, so a
  call ledger can be reconciled
  ([privacy](../privacy-and-llm.md#semantic-review-sends-both-texts)).

## Pre-frozen acceptance criteria

Frozen before the first call to the product model gateway. They are not edited
afterwards; a later change needs a new decision that says what changed and
why. They are measured on the owner's private evaluation corpus, which never
enters a repository: official Chinese/English pairs from one publisher (groups
A1–A6, used for the P and E layers) and monolingual Chinese community texts
(B1–B3, used for the M layer).

Layers: **P** semantic review on the official human translations (false
positives); **E** errors injected into those translations (recall); **M**
semantic review of new machine translations of monolingual texts; **M′**
precedent sub-run (ADR 0019); **G** regression set (MY-18 pairs, P22,
agent-built samples), regression only, never acceptance.

Before the first model call, a blind annotator lists every difference in
every aligned P pair and freezes each as **real error**, **allowed rewrite**
(localization practice or a limitation the corpus manifest records) or
**undecidable**, with the pair, both ranges and a reason. The list's SHA-256
goes into the evaluation ledger before the first call. An issue overlapping a
listed item lands on it. An issue on no listed item is judged afterwards in
the same three classes and reported separately as "off-list": an off-list real
error is neither a false positive nor added to the recall denominator; an
off-list allowed rewrite or model misreading is a false positive; an off-list
undecidable is reported on its own. E injections never fall inside an allowed
rewrite or undecidable range.

Semantic review gates:

- **E recall:** negation, quantity and omission at least 80% each; reference,
  meaning shift and term sense at least 60% each. At least 10 injections per
  class, spread over at least 3 groups.
- **P false positives:** per direction (zh→en and en→zh separately),
  medium- and high-confidence false positives (issues on allowed-rewrite items,
  plus off-list issues judged allowed rewrite or model misreading) at most 1
  per 1,000 Chinese characters. The denominator is always the Chinese side
  (about 8.4k characters in all), because the English side is about three
  times longer and would loosen the en→zh tolerance about threefold.
  Undecidable items are not in the numerator.
- **P real-error recall:** at least 60%, over the pre-frozen real-error items
  only. It counts toward the gate only with at least 10 such items; otherwise
  it is undecidable. The main recall evidence is E.
- **M precision:** medium- and high-confidence precision at least 60%, counted
  only with at least 20 such issues; otherwise undecidable. The owner's review
  of these issues is qualitative evidence; it neither fills the sample nor
  turns the item into a pass.
- **Anchoring:** 100% of returned issues have legal spans; unanchored drops at
  most 15%.
- **Bytes:** every evaluation response at most 56 KiB (guaranteed by the
  server; the receipt reports the maximum).
- **Latency:** per-segment P95 at most 30 s.

The translation-context gates are in ADR 0019. These rules cover both:

- **Three states.** Every gate is "met", "not met" or "undecidable (sample too
  small)", listed with its sample size. Any "not met" blocks merging the
  engine. With no "not met" but some "undecidable", the engine may merge
  (merging exposes nothing), but the PR, the receipt and the tracker say
  "n gates met, m undecidable", never "all met". An undecidable M′ gate falls
  back to the conservative default on its own (ADR 0019). Every other
  undecidable gate needs the owner's explicit acceptance of limited evidence
  in the review session, recorded in the receipt; one not accepted counts as
  not met and blocks every release.
- **Not met.** Report it as it is. Adjust only the prompt or the context
  organization, on evidence; no per-word exceptions and no model change. If
  the call budget's stop line is reached and a gate is still not met, the
  owner decides.
- **Reruns.** A rerun after tuning marks reused samples and keeps the first
  round's numbers; tuning on the same samples makes later numbers optimistic,
  and the report says so. Unused segments, if any, are held out and reported
  separately.
- **Budget.** At most 500 calls to the product model gateway, counting every
  translation and semantic review request including retries, the end-to-end
  check and post-deploy probes; annotation and adjudication sessions do not
  count. One ledger across runs; the stop line is 450 for the ledger total;
  evaluation itself stops at 420 to leave room for the end-to-end check and
  deploy probes.
- **Scope of the conclusion.** The evidence is official same-publisher pairs,
  injected errors and a small set of machine translations of community texts.
  It supports an internal acceptance, not a quality claim about independent
  human translations.

## Consequences

- Clients show two groups: "term constraints (surface match, deterministic)"
  and "semantic issues (model, may be wrong)".
- `/v1/reviews` stays the reproducible, zero-cost check; nothing that relies
  on it changes.
- A long range can be reported without a one-click fix. That is deliberate: a
  shortened executable range corrupts the translation.
- Every response fits the Web proxy by construction, at the cost of omitting
  issues on pathological input; the count of omitted issues is always visible.
